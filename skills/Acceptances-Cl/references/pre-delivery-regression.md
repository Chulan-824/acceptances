# 需求交付前全量回归

用于一个 Campaign 经多轮验证和评审后，对待交付版本开展整体回归。读取全部历史 Run 整理覆盖与反馈，再执行本轮检查；历史结果和人工通过不代替本轮验证。

## 确认输入与版本

从本次调用参数、自然语言和已有项目上下文取得 Campaign、当前需求版本或已确认的 PRD Snapshot、范围地图、涉及的业务目录、待交付版本和验证环境。浏览器回归方式按主流程步骤 5 选择，本场景不规定工具或操作脚本。任务输入不新增 `acceptances` CLI 参数或报告字段。

先复用主流程的关联与 Campaign 选择，不为全量回归创建新 Campaign。多仓库分别运行 `acceptances context --repo <目录>`，确认源码版本、dirty 状态与实际受验构建对应。正式交付的版本和材料要求见[正式交付材料](delivery.md)；需要提交代码但尚未获授权时，说明依赖，不自行提交或把 dirty 结果改写为干净版本。

需求版本、目标环境或范围存在实质歧义时，先读取现有资料；仍无法确定再询问，继续不依赖答案的盘点。只有历史 Run、没有可靠的当前需求范围时，不能据此宣称已覆盖整体需求。

## 盘点历史与编排清单

```sh
acceptances feedback --campaign <原Campaign标题或ID>
acceptances status --run <需核对的RunID>
```

读取返回的各轮报告、检查项、版本、`checkReviews` 当前人工判断、`reviews` 评论及 `feedbackResponses` 后续复验记录。列表默认隐藏合并归档的早期 Run，还需沿各轮 `consolidatedRuns[].sourceRunId` 用 `status` 读取；遇到反馈来源缺失或已删除记录，保留缺口，不能推断其内容。按[反馈处理](feedback.md)区分原始结果、当前判断和后续处理事实。

在本次 bundle 中维护一份 `regression-coverage.md`，作为普通附件保存，记录：

- 本次需求和地图版本、历史 Run ID 清单、已知资料缺口。
- 每个检查项的需求依据、来源 Run/check ID、相关反馈 ID、本轮 check ID，以及角色、前提、数据、环境、操作路径和预期。
- 重复项合并关系，以及因需求变更而不再适用的项及其依据。
- 执行后的逐项结果、证据引用、历史问题复验结论和未完成原因。

用当前需求和范围地图逐项核对历史清单，补齐尚无 Run 覆盖的行为，并纳入涉及多个功能的完整业务流程及相互影响的检查。只在前提、角色、数据、环境、路径和预期均相同时合并重复项，保留全部来源映射；相同 ID 或标题不足以判定重复。沿用行为和预期未变的稳定 check ID，预期实质变化时使用新 ID。

失败、阻塞、跳过、人工不通过和评论指出的问题均须核对后续处理及本轮覆盖。历史已人工通过的范围仍要重新验证；人已接受的限制继续记录，验证指令不自动授权修复。作废报告只作历史线索，不作有效证据。排除项须有当前需求或明确范围决策的依据，不能因执行困难而从清单删除；存在范围争议的项保留待确认。

## 执行本轮回归

按业务仓库的验证要求，在同一组待交付版本和约定环境执行完整清单，记录每项预期、实际结果与本轮证据。浏览器检查按本次选定方式开展，以实际页面、交互结果及必要的 API 响应判断；静态检查、模拟和真实页面/API 验证分别说明。旧截图、动作回执和历史人工通过不能作为本轮通过证据。

执行中发现问题时，保留失败并继续不受影响的检查；修复须有业务代码修改授权。源码或受验构建变化后，重新确认基线并重跑完整清单，使最终 Run 对应实际待交付版本，前一次结果保留为中间记录。

失败、工具不可用、权限不足和未执行的项按[报告格式](report.md)分别记录 `failed`、`blocked`、`skipped` 及具体原因。范围已确认、完整清单均纳入本轮并逐项记录真实结果时，按覆盖情况声明 `full`；实际只覆盖局部时用 `partial`，完整范围无法确定时用 `unknown`。完整范围不表示全部通过，仍有失败、阻塞或跳过时不能宣称全量回归通过。

## 归档与交接

实际验证使用新 bundle 和新 Run，归属原 Campaign。将覆盖清单声明为 `report.evidence` 中的普通附件，在 `scope` 中概述覆盖范围和缺口，在 `description` 中说明它对应的历史 Run 与清单附件；环境字段记录实际工具和受验环境。其他报告字段及附件要求复用[报告格式](report.md)，不改写历史 Run、不拼接历史通过结果。

当前 `followUp` 只支持一个来源 Run。用户指定来源时按该来源填写；否则可为本轮实际响应的一份来源 Run 按[反馈处理](feedback.md)填写。多轮反馈的完整来源 Run/review ID、本轮 check ID、处理说明和复验结果保存在覆盖清单中，不把其他 Run 的反馈塞入同一个 `followUp`，也不新增未支持的字段。附件中的映射不会生成系统反馈关联或自动关闭原反馈。

本次还要求准备正式交付时，在验证前读取[正式交付材料](delivery.md)，将需求原文、范围地图、说明素材、实际构建和本轮证据随同一个最终 Run 归档。复用主流程步骤 6、7 预检、发布和核对回执。正式预检不通过时说明材料或范围缺口，保留本次待发布包，不能缩减清单以获得通过。

交接时给出最终 Run 的 `webUrl`、需求及受验版本、覆盖项数和结果计数、历史问题复验结果、失败/阻塞/跳过及资料缺口。明确是否已完成完整范围的回归、是否仍有阻止交付的问题。新 Run 的人工判断从待审开始，由用户评审和确认正式交付；归档成功不等于需求已交付。
