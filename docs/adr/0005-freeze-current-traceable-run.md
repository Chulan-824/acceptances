# 正式交付只冻结最新且版本明确的完整验证

2026-10-13，用户在需求对齐中确认，Delivery Snapshot 只能绑定确认时仍是当前 Campaign 最新、非作废、完整且全部检查项人工接受的 Run；存在新一轮后不能选择历史已接受 Run 冻结。最新沿用成功发布顺序，不按报告中的验证时间推断。该选择沿用当前需求整体通过的范围，避免新一轮仍待审时将旧结果作为当前正式交付。

用户进一步确认，源码或实际运行构建版本未知、空缺或无法关联时阻止冻结，不提供填写理由后绕过的例外。普通报告继续如实归档未知信息，已有人工判断保留；正式交付的版本要求独立于归档和人审。这比现有允许 unknown 的报告协议更严格，用于保证交付证据能对应明确版本。

用户随后确认，正式冻结只允许实际验证时源码已提交且 dirty=false 的版本，dirty=true 或未知均不满足门槛。含未提交改动仍可归档和人审；正式交付需先提交，再针对该版本实际验证，不改写旧报告，也不在一期增加未提交源码快照的交付协议。此要求不涉及合并 master 或推送。

用户确认原始含 failed、blocked 或 skipped 的检查项，只要全部人审接受且其他门槛满足，也允许冻结。冻结确认列出这些项，快照保留原始结果和当时人工判断，业务说明披露相关限制，不把人工接受写成验证通过。正式交付继续尊重人工判断，不额外要求机器结果全部 passed。

用户进一步确认，每个原始非 passed 但已人工接受的项，冻结前必须有具体接受理由。与当前接受判断对应的已有具体理由可以沿用；缺失时在冻结确认中逐项补填，随快照保存。一键接受的统一说明不能代替具体理由。该要求只约束正式冻结，不改变已有批量人审无需理由的规则，也不修改原报告或增加虚假的验证 Run。

用户确认冻结前必须核对选定需求地图的必验项。每个必验项都必须在同一最终 Run 中有对应检查项，完全缺项时阻止冻结，不仅依赖 full 声明或跨轮历史结果。原始非 passed 但已明确记录的检查项，继续按已确认的人工接受和具体理由规则处理。平台检查结构覆盖，地图本身是否列全需求及证据是否充分仍由人审。

用户进一步确认，在同一次冻结确认中明确认可所选地图版本及必验范围，并将这次范围确认记入快照。接受全部检查项不自动视为认可整个地图；所选地图版本或内容变化后须重新确认，不能沿用旧版范围确认。这只确定产品流程，不代表已认可当前业务候选地图或批准试跑。

构建与版本证明的具体格式、地图身份与版本及素材门槛，以及冻结后的撤销、替代和删除保留，继续在[规划对齐记录](../../.scratch/delivery-snapshot-business-doc/spec.md)中确认。本决策尚未实施，不修改 ADR-0001 至 ADR-0003 中既有归档、人审或一键接受的行为。
