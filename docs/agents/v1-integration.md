# 本地项目与 Agent 接入

先按 README 启动服务，在 Web 注册并登录后创建 Project。安装新版 CLI 和 `Acceptances-Cl` skill 后，从业务目录调用 skill，选择已有 Project。关联保存在宿主机，后续调用复用；同仓库 worktree 共用关联，多仓库可归属同一 Project。

CLI 需要与 Web 相同的平台账号。先在本机执行 `acceptances login --url <API地址> --username <用户名> --password-stdin`，由用户通过标准输入提供密码；会话按服务地址保存在私有配置文件中，Agent 不读取或回显凭据。后续命令复用会话；401 时请用户重新登录。CLI 不需要旧 contracts 目录。容器不读取业务代码，实际测试由宿主机 Agent 执行。CLI 命令和报告示例以 [skill 工作流](../../skills/Acceptances-Cl/SKILL.md)和[报告格式](../../skills/Acceptances-Cl/references/report.md) 为准。

浏览器验证方式由本次调用参数或自然语言指定；未指定时结合当前会话已明确的用户偏好、业务仓库规则和实际可用工具选择。指定方式不可用时说明阻塞，继续其他可执行检查，不因本机已有配置自动换用其他方式。本次选用 Jev 时才读取 skill 的[可选 Jev 执行](../../skills/Acceptances-Cl/references/jev-browser.md)。安装器仅记录可选源码路径，不分发私有配置，部署服务不提供共享 Key。

## 交付一次验证

1. 确认需求对应的 Campaign。复验继续使用同一 Campaign。
2. 在真实业务环境执行本次检查。用 `scopeType` 明确完整、局部或未知，`scope` 说明具体覆盖及未重跑内容。未执行、失败或未知信息如实填写。
3. 准备一份结构化报告及截图、录像、日志等附件。报告包含标题、说明、验证时间、范围、环境、代码版本及 dirty 状态、检查项预期与实际结果。反馈复验按报告格式填写 `followUp`。
4. CLI 整包提交，保存提交 ID。网络中断后复用原 ID 和原内容重试；新一轮实际执行才产生新提交。
5. 读取保存结果与人工反馈。报告归档成功不代表通过或人工接受。

同 ID 同内容返回既有 Run，不重复创建；同 ID 不同内容返回冲突。全部附件和报告保存后才可见。局部复验明确展示范围，不跨 Run 自动合并通过结果。

## 需求交付前全量回归

多轮验证后准备整体交付时，按 skill 的[需求交付前全量回归](../../skills/Acceptances-Cl/references/pre-delivery-regression.md)结合当前需求、范围地图、全部历史 Run 和反馈整理完整清单，在待交付版本上重新验证。补齐历史未覆盖的需求及跨功能流程，保留重复项合并、需求变更和多轮反馈的来源映射。实际完成后向原 Campaign 保存新的最终 Run，归档覆盖清单及本轮证据；失败、阻塞、跳过和资料缺口如实交接，人工评审及正式冻结仍由用户完成。

## 人工反馈与纠错

用户在 Web 对每个检查项通过、不通过、撤回到待审或评论。逐项人工不通过须填写理由；原始结果为 `failed`、`blocked`、`skipped` 时逐项人工通过也须理由。普通通过和撤回理由可选，评论须非空。

系统以最新明确判断计算各项人工状态，保留每次操作历史。评论不改变状态。任一项不通过则整轮不通过；没有不通过但有待审则整轮待审；全部人工通过才整轮通过。人工可接受 Agent 未通过的项，原始结果继续显示。

用户也可在当前 Run 点击“批量人工通过”，确认汇总后批量通过全部检查项，可覆盖已有不通过判断；批量通过无需填写理由，逐项操作继续保留原理由规则。已通过项跳过，原历史保留；搜索和筛选不缩小交付范围。全部人工通过即本轮已验收，后续仍可改判或撤回，详见 [ADR-0003](../adr/0003-bulk-human-acceptance.md)。

Campaign 仅由最新 Run 决定。只有最新完整范围 Run 全部人工通过才 Campaign 通过，局部或未知范围 Run 通过后 Campaign 仍待审。新 Run 的各项重新待审，历史改判不改变当前需求，不跨轮继承通过。

已保存报告及附件不能覆盖，范围和复验响应也随报告保留。文字错误用补充说明，整体错误作废并填写原因。作废状态优先，可继续评论，但不能通过、不通过或撤回。

Web 删除前展示影响范围，删除同时清理所属原报告、证据和反馈。已冻结交付的独立快照、复制证据和说明保留，删除来源使对应交付失效。删除最新 Run 后 Campaign 待审，不恢复历史接受。

## 正式冻结与业务说明

用户要求正式交付时，发布前按[正式交付材料](../../skills/Acceptances-Cl/references/delivery.md)准备版本清单、需求原文、地图、结构化说明和真实截图。现有 publish 上传普通附件即可，Report schema 不增加未知字段。源码、实际构建、范围覆盖及材料不满足门槛时仍可如实归档，但不能正式冻结。

用户在 Web 对最新完整且全项人工接受的 Run 明确冻结，同时确认地图版本/范围、说明内容及敏感信息检查，并为原始未通过项记录具体理由。Agent 准备材料和读取反馈，不代替人作出这些确认。

交付内容不可变，效力通过追加事件表达。改判、撤回、作废或删除来源使其失效；重新接受须再次明确冻结。来源删除后可从首页交付版本读取独立证据及历史说明。

有效交付可确定性生成离线 HTML，说明独立版本、预览/下载、失败重试均不修改原 Run 或快照；失败、失效及来源缺失如实展示。接口行为见[交付协议](../../contracts/delivery.md)，材料格式以 skill 引用为准。

## 评论后的修复与复验

保存评论后，在业务聊天中要求 Agent 读取反馈。修复需用户授权，验证指令本身只授权验证；Acceptances 不自动唤醒或调度 Agent。

```sh
acceptances feedback --campaign <标题或ID>
acceptances status --run <指定来源RunID>
```

Agent 读取 API 返回的 `checkReviews` 当前判断、`reviewCounts` 计数及 `reviews` 历史，按当前人工不通过项、相关评论和本次指令确定处理范围。旧规则下 `legacy: true` 的整轮判断只提供历史背景。人工已通过的项不因 Agent 原始失败自动要求修复。

完成实际验证后，用新的 bundle 向同一 Campaign 发布。`followUp.sourceRunId` 指定来源，每个响应填写真实 `reviewId`、非空 `explanation` 和本轮 `checkIds`。同一报告中，同一反馈只填写一个响应；未处理、无需改动或受阻可以没有关联检查项，但须说明原因。整轮评论提出的新行为在新报告新增检查项。

`feedbackResponses` 可从原反馈找到后续 Run，`status --run <后续ID>` 可查看处理说明和复验证据。这些响应不关闭原反馈、不继承人工判断，用户重新逐项评审。来源之后被删除，后续 Run 保留原引用及说明，并通过 `sourceRunAvailable: false` 表示来源不可读。

CLI `publish` 原样上传报告；`publish`、只读 `status` 和 `move-run` 添加完整 Run 路由的 `webUrl`，其余 API 字段保留。`--url` 是 API 地址；API 与 Web 分离时，用 `acceptances link --url http://127.0.0.1:8765 --web-url http://127.0.0.1:5173 --project <名称或ID>` 保存两个入口。同源部署省略 `--web-url`，默认复用 API 地址。旧关联可对同一 Project 重新 link 更新；只修正回执时运行 `status --run <ID>`，不创建或移动 Run。字段细节和执行顺序见 [反馈处理](../../skills/Acceptances-Cl/references/feedback.md)。

## 存储升级

当前日常服务使用 Docker MySQL。当前数据库备份和恢复边界见 [MySQL 存储](../mysql-storage.md)，不改变 CLI/skill 的 HTTP 协议。

### 数据库兼容

当前运行时仅支持 MySQL。历史 SQLite 升级记录保留于 Git，不再提供对应启动或导入入口。旧报告缺少 `scopeType` 仍可提交，视为范围未知，原包重试继续使用原内容。

日常运行库升级先保存一致的数据库与附件备份，核对真实数据卷，按[实施交接](../v1-implementation-handoff.md)验证迁移。仅编辑源码不表示容器、宿主机 CLI 或已安装 skill 已升级。

当前所有登录用户具有相同操作能力，记录操作身份，但不拆分提交与人工评审权限。Agent 不自动替用户接受报告。验证指令不授权 Agent 修改业务代码。
